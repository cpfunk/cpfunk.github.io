Creating a RISC-V Microprocessor for Micro Quadcopter Applications

Project Overview

For my senior design project, a team of other EE and CprE seniors and I are creating a microcontroller (MCU) that has interfaces and features targeting high-performance micro quadcopter applications like the Crazyflie 2.1.

The MCU we are creating features support for protocols such as SPI, I2C, UART. It also features PWM support for controlling the quadcopter's motors, PID acceleration for controlling the PWM outputs, and a Trigonometric Unit (TMU). This TMU enables the efficient processing of positional data from the Inertial Measurement Unit (IMU). We plan to have this microcontroller fabricated in the spring using the Sky130 open-source process.

Big Picture Contribution

Due to the small size of the circuit boards on microquadcopter drones, and because of the need to minimize power consumption, these microquadcopter drones feature only one microcontroller for both reading in sensor data from the inertial measurement unit, controlling all four rotors, and recieving and responding to remote control signals from the bluetooth chip. Since the microcontroller's main thread is occupied with processing these inputs, this leaves little overhead for running other processes that a user may want to perform with the drone, like video processing. Our microcontroller design aims to unburden the microquadcopter's main thread by implementing a microcontroller architecture that features parameter, integral, derivative (PID) acceleration. This will allow the PID control of pulse width modulated (PWM) outputs (which are used to control the motors) to occur separately from the microcontroller's main thread, and will enable a the quadcopter to process other tasks with its main thread without a second microcontroller, and with little impact to the drone's power consumption.

My Role

My role in this project involves selecting SPI and I2C cores and creating a wishbone to TL-UL that will enable these cores to interface with the other on-chip devices connected to the wishbone bus. I am also involved in testing various pieces of hardware on the microcontroller, like the I2C interface and the SPI interface. I am also the team's documentation lead, so I am responsible for creating and maintaining this project's documentation.

Skills or Knowledge Gained

Through this project, I am learning how to perform randomized unit testing using SystemVerilog. I am also learning the process of verifying a digital chip such that we can be confident that it will work once it is fabricated. This verification process involves running both gate-level and FPGA simulations. Since I am responsible for implementing modules that communicate via the I2C, SPI, wishbone, and TL-UL protocols, I have been able to learn about how these various communication protocols operate.

Resources Used

  • All of the members on the team have experiencing designing a RISC-V processor, however, to speed up development time and enable a more focused approach to engineering and creating the core features that set this microcontroller apart, we chose to use a pre-tested open-source 32-bit RISC-V processor IP. For this project, we chose to use a VexRISC 32-bit RISC-V processor IP.
  • In creating this project, our team used ChipFoundry's CLI to synthesize the Verilog HDL, run simulations, and perform place and route.
  • We also referenced "The CORDIC Trigonometric Computing Technique" by Jack E. Volder when designing our CORDIC-based TMU.
  • In selecting the IP cores for the I2C and SPI interface modules, we referenced the technical documentation for the Bosch BMI088 IMU since this is the IC that would require I2C and SPI interface module in our target application.
  • When designing the SPI interface, we referenced "SPI Interface Specification" by VTI Technologies.
  • When designing the UART interface, we referred to "UART: A Hardware Communication Protocol Understanding Universal Asynchronous Receiver/Transmitter" by Peňa and Legaspi, published in AnalogDialogue.
